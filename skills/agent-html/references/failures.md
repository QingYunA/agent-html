# 失败记忆 · Failure Log

> **规范和失败记忆解决不同的问题。** 规范告诉 Agent「该做什么」，失败记忆告诉它「不要再重蹈什么」。
>
> 每条固定四段：**症状**（用户/读者看到什么）→ **根因**（为什么会这样）→ **规则**（下次怎么避免）→ **复查**（怎么自动或人工发现它）。
>
> 若一条失败能被机器判定，**复查**必须给出规则编号；若不能，必须显式写明「无法自动校验」。宁可承认测不了，也不要制造「门禁通过 = 没问题」的错觉。

---

## F-001 · 校验规则用子串匹配，导致永远不报

**症状**：模板缺了 `--primary` 变量定义，校验器仍然显示 PASS。规则形同虚设，而且没人能发现，因为「它从来没报过」。

**根因**：判定写成 `content.includes('--primary')`。模板里有 `--primary-fg: #fafafa;`，子串包含 `--primary`，条件恒真。

**规则**：校验 CSS 自定义属性是否存在时，必须匹配**声明形式**（`--primary\s*:`），不能匹配裸名字。任何 `includes()` 做「存在性判断」的地方都要问一句：会不会被更长标识符满足？

**复查**：`scripts/test-rules.mjs` 的 `[THEME_TOKENS]` 用例（剥掉 `--primary:` 但保留 `--primary-fg:`，断言必须报错）。

## F-002 · 门禁误报会摧毁对门禁的信任

**症状**：第一版规则上线，20 个文件里报出 9 处「硬编码颜色」。逐一查看后发现**全部合法**——6 处是 `:root` 里的 `--card: #ffffff` 令牌定义，3 处在 `@media print` 块内。

**根因**：规则只看「有没有出现 `#fff`」，不理解「在哪个作用域出现」。令牌定义块与打印块里的字面量本来就是合法的。

**规则**：**白名单先于规则。** 写任何规则前，先列出它的合法例外并实现排除逻辑；否则 Agent 一旦发现 lint 会误报，就会开始整体无视它，比没有门禁更糟。

**复查**：语义上——`scripts/validate.mjs` 中 `TOKEN_SELECTOR` 与 `PRINT_SELECTOR` 的排除；机制上——`scripts/test-rules.mjs` 的反向用例（白名单用例必须不报）。

## F-003 · 豁免作用域过粗，会掩盖同文件其他真实缺陷

**症状**：为了放行「代码块上的复制按钮」这一处合法的硬编码深色，最初把豁免做成了**文件级**——结果整个文件里再出现任何真实的暗黑模式泄漏都不会再报。

**根因**：`@lint-allow` 按规则名收集成 `Set`，检查时 `if (allows.has(ruleId)) continue`，粒度是文件。

**规则**：豁免的作用域应当是**命中点本身**（实现为「注释所在行 + 下一行」），而不是文件。任何豁免机制都要回答：它会不会顺带放过别的什么？

**复查**：`scripts/test-rules.mjs` 的「豁免必须有作用域」用例（豁免一处后，同文件另一处的泄漏仍须被捕获）。

## F-004 · 豁免不写理由就等于没有豁免

**症状**：豁免注释可以随意写，`/* @lint-allow: DARK_MODE_LEAK */` 就能静默关掉规则。半年后没人知道当初为什么放行。

**根因**：豁免只解析规则名，不校验理由。

**规则**：豁免**必须带理由**，且理由长度不足（<4 字符）时视为无效、不生效。理由写在命中点的上一行，让下一个读者不必翻 commit。

**复查**：`scripts/test-rules.mjs` 的「豁免必须写理由」用例。

## F-005 · 「恒定深色表面」上的硬编码色是合法的

**症状**：代码块的复制按钮用了 `background:#3f3f46; color:#fff`。规则报错，但直觉说这是对的。

**根因**：该按钮悬浮在 `.code-box` 上，而 `.code-box` 的底色是 `#18181b`——**它刻意不随主题反转**（终端隐喻）。在这个表面上硬编码白字是正确的，换成 `var(--primary-fg)` 反而会在暗色模式下错色。

**规则**：判定「硬编码颜色」要看它**所在表面的语义**，不能一刀切。遇到恒为深色的表面（代码块、终端、日志面板），正确做法是**加豁免并写明该不变量**，而不是改颜色去讨好规则。**永远不要为了通过 lint 而把正确的代码改错。**

**复查**：无法自动校验。依赖写入豁免注释里的理由供人工复核。

## F-006 · 文档承诺的结构，某个语言版本没兑现

**症状**：`SKILL.md` 明确写着 Report 母版包含「悬浮目录（Sticky TOC with ScrollSpy）」，但英文版 `en/report.html` 里 `nav`、`aside`、`IntersectionObserver` 全部为 0——中文 695 行，英文 441 行。读英文模板的 Agent 会照着一个残缺骨架干活。

**根因**：模板以中文为事实上的正本先行开发，英文版是后补的简化版，且**没有任何机制检查两者同构**。

**规则**：中英母版必须**结构同构**。差异要能被机器发现，而不是靠人去比对两个文件。

**复查**：`scripts/validate.mjs` 的 `[ZH_EN_PARITY]`（中文有而英文为零的 `<nav>` / `<aside>` / `<details>` / `<table>` / `<dialog>` / `<section>` 判为阻断；同一功能的导出按钮 id 不一致判为提醒）。

## F-007 · 硬编码颜色在暗黑模式下让图形整个隐形

**症状**：英文版 dashboard 的面积图在暗色主题下**完全看不见**。

**根因**：渐变写死 `stop-color="#18181b"`。这个值等于浅色主题的 `--primary`；而暗色主题下 `--primary` 是 `#fafafa`。于是**深色卡片上画深色渐变**。中文版用的是 `var(--primary)`，所以只有英文版出问题。

**规则**：SVG 内的所有着色必须走 CSS 变量或 `currentColor`。这类 bug 只在你**真的切到暗色主题看**的时候才暴露。

**复查**：`[CHART_TOKEN_ONLY]`（静态）＋ `scripts/smoke.mjs` 的暗黑模式切换探针（运行时）。

## F-008 · 有筛选但无空状态

**症状**：用户在搜索框里输入一个不存在的关键词，表格区域变成一片空白，看起来像页面坏了。

**根因**：只实现了「过滤」逻辑，没实现「过滤结果为空」的分支。仓库里 6 个产物都有这个问题，**包括组件画廊页**——而画廊正是 Agent 学习「正确写法」的参考实现，所以缺陷会被复制到下游产物。

**规则**：任何实现 `addEventListener('input')` 或 `filter()` 的列表/表格，**必须同时实现空状态**。空状态元素放在被筛选容器**之外**（放进 `<table>` 内会污染文本匹配），用主题变量着色。

**复查**：`[EMPTY_STATE]`（静态）＋ `scripts/smoke.mjs`（运行时）。

## F-009 · 打印时内容被截断 / 多印空白页

**症状**：导出 PDF 时操作按钮一起被打出来；工作台型页面只印出可视的一屏；看板被压成 2 列；甚至正文只有一页高却多印一张空白页。

**根因**（四个独立成因，都在同一次排查中出现）：
1. 4 个母版根本没有 `@media print` 块；
2. 工作台用 `height:100vh; overflow:hidden`，打印时按可视高度分页；
3. 窄的打印断点（A4 约 794px）命中了 `max-width:992px`，把 4 列看板折成 2 列；
4. `body { min-height:100vh }` 把 body 撑到 1123px > 可印区 1047px，尾部内容被挤到第 2 页。

**规则**：文档型页面必须有 `@media print`：隐藏交互 chrome、解除 `100vh` 与 `overflow` 裁剪、给重复卡片加 `break-inside: avoid`、用 `!important` 锁定多列栅格、解除 `min-height:100vh`。**注意 `height:auto` 覆盖不了 `min-height:100vh`**，要看原声明是哪一个再对症下药。

**复查**：`[PRINT_STYLE]`（静态，只能查有无）＋ 打印媒体实测（`Emulation.setEmulatedMedia({media:'print'})`，目前未纳入自动门禁）。

## F-010 · 同一语言中立路径下挂着特定语言的内容

**症状**：`templates/<name>.html` 与 `templates/zh/<name>.html` **字节完全相同**，且全仓零引用；但 CLI 的 fallback 正指向前者。也就是说：语言中立路径下挂着中文内容，只在 `en/` 缺失时才可达——一颗定时炸弹。

**根因**：早期只有一种语言，路径是 `templates/`；后来加语言目录时把旧文件留在原地当 fallback，忘了它们会随中文版演进一起漂移。

**规则**：每个产物**只能有一份真实正本**，其余必须是软链或语言变体。新增语言目录时必须同步处理旧路径，并检查有无引用。

**复查**：`bin/cli.mjs` 的模板解析（fallback 已改指 `templates/zh/`）；新增软链后无死副本可删。

## F-011 · 自测脚本自己写了死代码分支

**症状**：烟测脚本里有一条断言 `if (toggled && before.bg === after.bg)`，永远不会触发——因为 `toggled` 的定义就是 `before.bg !== after.bg`，两个条件是互斥的。

**根因**：写断言时没有回头检查条件之间是否自相矛盾。

**规则**：**门禁脚本本身也要有变异测试。** 一条永远不触发的断言和一条永远通过的规则一样，都是装饰。

**复查**：`node scripts/smoke.mjs --selftest`（注入缺陷，断言探针确实能失败）。

## F-012 · 用 `for` 循环 + `&&` 写守卫，守卫不会生效

**症状**：写了一段「逐个校验文件哈希，任一不符就中止」的删除守卫，其中一个文件确实不符并打印了「中止」——**但删除照常执行了**。

**根因**：`for ... done && rm ...` 的退出码取自**循环里最后执行的命令**，而那是 `echo "中止"`，退出码 0。守卫打印了警告却没有阻断。

**规则**：shell 里的守卫必须在循环内**显式 `exit 1`**（或累加失败标志后在循环外判断），不能依赖循环的退出码。**打印了警告不等于阻止了操作。**

**复查**：无法自动校验。属于破坏性操作前的自查清单项。

## F-013 · 规范文档自身的结构损坏

**症状**：`SKILL.md` 里出现两个 `## 二` 且没有 `## 五`；文件末尾还孤零零挂着一个未闭合的 ```` ``` ````。前者让「见第二节」这类交叉引用指向错误的位置，后者会让**后续全文在某些渲染器里变成代码块**——Agent 读到的规范可能是错的，而且它不会报错。

**根因**：章节是增量追加的，中间插入新章节时忘了重编号；代码围栏靠手写复制，少写一个 ```` ``` ```` 不会有任何即时反馈。两个缺陷都**在仓库里存活了很久**，因为没有任何东西检查文档。

**规则**：**规范文档要当代码一样校验。** 章节编号不得重复或跳号；代码围栏必须配对；交叉引用一律**按名称**（「反模式规避清单」一节）而不是按编号——这样重编号不会改坏引用。

**复查**：`[DOC_FENCES]`（阻断）、`[DOC_SECTIONS]`（提醒）。两者都只对 `.md` 生效（规则的 `scope` 字段）。

## F-014 · 文档样例引用了基座里根本没定义的 CSS 变量

**症状**：`references/components.md`、`README.md`、`README.zh-CN.md` 里的图表样例用了 `var(--chart-indigo)` 等 7 个 `--chart-*` 变量，而 `SKILL.md` 要求 Agent 复制进每个产物的那段 Micro-CSS 基座里**没有这些变量**。实测：

```
--chart-indigo               → (未定义)
stroke=var(--chart-indigo)   → none            ← 线直接不可见
stroke=var(--primary)        → rgb(24,24,27)   ← 对照组正常
```

也就是说：**严格按文档流程做出来的页面，抄了文档里的图表代码，画出来是空白的。** 37 处引用全部失效。只有画廊页 `index.html` 自己定义了这些变量，所以看起来一切正常——**缺陷只存在于「照文档做」的路径上，而文档作者走的是画廊路径。**

**根因**：变量定义只在画廊页演进，基座 CSS 是另一份手抄副本，两者之间没有任何一致性检查。另外 `var()` 不带 fallback 时属性是**整体失效而不是降级**，所以错误表现为「图形消失」而非「颜色不对」，更难被发现。

**规则**：单文件零依赖下没有外部样式表，**任何 `var(--x)` 引用的变量必须在同文件内定义**；跨文档同理——文档承诺的基座就是 token 全集，其余文档的代码样例不得引用基座之外的变量。

**复查**：`[CSS_VAR_DEFINED]`（HTML 产物，阻断）＋ `[DOC_TOKEN_COVERAGE]`（跨文档样例，阻断）。

## F-015 · 门禁全绿，图依然是错的

**症状**：写 `examples/gate-baseline.html` 时，画了一张**水平**条形图（值轴在 X：0 在左、15 在右）。但我把数值刻度 `15 / 10 / 5 / 0` 标在了**左侧的 Y 轴**位置，还画了三条**水平**虚线当导轨。结果是：

- 那四个刻度不对应任何真实维度（Y 轴是类目，不是数值）；
- 它与页面底部的 `0 / 5 / 10 / 15` 刻度**互相矛盾**；
- 水平导轨纯属装饰，不携带任何信息。

**当时 18 条校验规则、14 个产物烟测、28 个变异用例全部通过。** 因为这不是"工程缺陷"，是"图理解错了"——没有任何静态检查能发现。

**根因**：写 SVG 时套用了"柱状图 = 有 Y 轴刻度 + 水平导轨"的记忆模板，而没有先问「这张图的视觉通道分别对应哪个数据维度」。这正是反模式 15「颜色/刻度必须连接真实维度」和「数值与视觉严格成正比」的违例——只不过违例的是**刻度**而不是颜色。

**规则**：画任何图之前先答「本体问题」：每个视觉通道（位置 / 长度 / 角度 / 面积 / 明度 / 刻度）**分别**对应哪个数据维度？答不出来就别画。水平条形图的值轴在 X，导轨必须是**竖直**的。

**复查**：**无法自动校验。** 这类错误必须靠人眼看一眼图，或者靠下面这条启发式自查：
> 把图上的每一条刻度线、每一个刻度数字遮住，问自己「它对应数据里的哪一列？」——答不上来的，删掉。

**这件事最值得记住的地方**：它证明了「门禁全绿 ≠ 图是对的」。`SKILL.md` §七 里那句「脚本全绿只证明工程上没坏，不证明图上没错」不是免责声明，是真实发生过的事故。

## F-016 · 文档引用的资产没有随技能一起分发

**症状**：`SKILL.md` 让 Agent 执行的 `node scripts/validate.mjs`，在技能被安装后**这个文件不存在**。因为三个自验脚本放在仓库根的 `scripts/`，而技能只包含 `skills/agent-html/`。`npx skills add` 复制的是技能目录，`bin/cli.mjs install` 也只软链技能目录——两种安装方式都拿不到脚本。

更隐蔽的是：**在仓库里开发时一切正常**（cwd 恰好是仓库根，`scripts/` 就在眼前），所以这个 bug 只有站在「已安装用户」的视角才看得见。这与 F-014 是同一类——**文档描述的能力在文档描述的使用方式下不成立**。

伴生的第二个问题：脚本全部用 `process.cwd()` 解析路径，即使把它们塞进技能目录，从任意工作目录调用依然找不到资产。

**根因**：把「技能资产」和「仓库开发工具」混在同一个 `scripts/` 里。技能是有边界的分发单元，边界外的文件不会跟着走。

**规则**：
1. **凡是 `SKILL.md` 让 Agent 执行的东西，必须位于技能目录之内。**
2. 脚本解析路径一律相对**脚本自身位置**（`import.meta.url`），不用 `process.cwd()`。
3. 区分两类脚本：**技能资产**（Agent 会用，如 `validate.mjs` / `smoke.mjs`）放技能内；**维护者工具**（如 `test-rules.mjs`、截图脚本）留仓库根。

**复查**：把技能目录复制到一个空环境（如 `/tmp/installed/.agents/skills/`），从无关的工作目录运行其中每个被 `SKILL.md` 点名的命令。**这条应该常规化**——它是唯一能发现此类问题的办法。
